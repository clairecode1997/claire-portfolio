03H3 地理空間分析H3 Geospatial Analysis

使用 Uber H3 六邊形格網系統，對新竹市五種城市圖層與台北西區 12 年人口資料進行空間索引化與視覺化分析。H3 讓不規則的行政區邊界轉換為標準化的六邊形格子，可以直接做跨資料集的空間比較。 Used Uber's H3 hexagonal grid to spatially index and visualize five Hsinchu urban layers and 12 years of Taipei West population data. H3 converts irregular administrative boundaries into standardized hexagonal cells, enabling direct cross-dataset spatial comparison.

H3 的核心優勢：把地球表面切割成多解析度的六邊形格子，每格有唯一 Hex ID。相較於行政區，六邊形在空間密度計算上更均勻、視覺上更直觀，且可在不同解析度之間做父子映射（res 15 → res 12 → res 9）。 Why H3: Divides the Earth's surface into multi-resolution hexagonal cells with unique IDs. Compared to administrative units, hexagons give more uniform spatial density and intuitive visualization, with parent-child resolution mapping (res 15 → res 12 → res 9).

視覺化洞察：總數 vs. 密度的選擇至關重要——同一份資料用人口「總數」渲染時，大面積行政區會被放大；改用「密度」後，實際人口集中的市中心才會突出。兩張圖說的是不同的故事。 Visualization insight: total count vs. density is a critical design choice — the same data rendered by total population inflates large administrative areas; density reveals where people actually concentrate. The two maps tell fundamentally different stories.

04City AI 介面改版City AI UI Redesign

City AI 是 CSL 的城市資料 AI 分析平台，使用者可以用自然語言查詢城市資料，系統透過 Multi-Agent 架構在背景取資料、分析，並把結果渲染到地圖上。我負責將原有的多頁版介面收斂為「單頁版」，並設計 Multi-Agent 溝通過程的視覺化呈現。 City AI is CSL's urban data AI analytics platform — users query city data in natural language; the system fetches, analyzes, and renders results onto a map through a Multi-Agent architecture. I led the redesign from a multi-page layout to a single-page interface and designed the visual language for the Multi-Agent communication process.

核心問題：AI 是一個黑盒。使用者輸入查詢後不知道 AI 在做什麼，也不知道什麼時候會得到結果。Multi-Agent 系統讓這個問題更嚴重——背後有 Planner、Data Fetcher、Map 等多個 Agent 協作，但使用者完全看不到。 Core problem: AI is a black box. Users had no visibility into what the AI was doing or when results would appear. The Multi-Agent backend — Planner, Data Fetcher, Map Agent — made this worse; all of it was invisible.

06反思與收穫Reflections

🔩 從資料到介面的垂直整合 🔩 Vertical integration: from data to interface

這次實習最特別的地方是同時做了底層資料（Pipeline + H3）和上層介面（City AI UI）。這讓我在設計 UI 時能真正理解資料的邏輯，也在建立資料管道時知道下游使用者需要什麼格式——而不是各做各的。 What made this internship unusual was doing both the data layer (pipeline + H3) and the interface layer (City AI UI). This meant I could design the UI with genuine understanding of the data's logic, and build the data pipeline knowing exactly what format downstream users needed — not two teams working in silos.

💥 「資料庫整個搞壞了」的那一次 💥 That time we broke the database

在處理大規模資料集時，我們曾經不小心對 Lab 的 PostgreSQL 資料庫做了不可逆的操作，讓當時的分析工作暫時中斷。這件事讓「不要直接在 prod 環境操作」從一句話變成有血有肉的記憶——同時也讓我對 dbt 的設計哲學（轉換邏輯與實際資料分離）有了更深的理解。 While handling a large dataset, we accidentally made an irreversible operation on the lab's PostgreSQL database, temporarily stalling our analysis work. "Never operate directly in prod" went from an abstract rule to a vivid memory — and deepened my appreciation for dbt's design philosophy of separating transformation logic from actual data.

📏 大規模資料的感知 📏 Developing a sense for data scale

在本機的 Jupyter 上跑 350 萬筆資料，「跑完了嗎？」是常態。這讓我學會在動手之前先估算資料量，選擇合適的處理方式（向量化 vs. 迭代）；也學會了在 Lab 伺服器環境上處理本機跑不動的資料。 Running 3.5M rows on a local Jupyter instance made "is it done?" a regular experience. I learned to estimate data volume before starting, choose appropriate processing strategies (vectorized vs. iterative), and use the lab server for what local machines couldn't handle.

最大的 Mindset 轉變：LLM 是加速器，不是替代品。在不熟悉的技術棧（Airflow、Kubernetes、H3）裡，我大量使用 LLM 幫助理解文件和除錯。但要能判斷 LLM 的答案是否正確，必須自己先有基礎概念——而建立基礎概念這件事，還是得靠自己動手。 Biggest mindset shift: LLMs are accelerators, not replacements. Working in an unfamiliar stack (Airflow, Kubernetes, H3), I used LLMs heavily for documentation and debugging. But judging whether an LLM's answer is correct requires your own foundational understanding — and building that foundation still requires doing things yourself.
