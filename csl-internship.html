02Urban Data Pipeline — 城市資料 ELT 基礎建設Urban Data Pipeline — City ELT Infrastructure

從零建立一套完整的城市資料收集與轉換系統，讓研究員可以持續、自動地把政府開放資料納入分析資料庫。技術選型遵循現代 data stack 標準：Airbyte 負責 E（抽取）與 L（載入），dbt 負責 T（轉換），Airflow 負責整個流程的排程與監控。 Built a complete city data collection and transformation system from scratch, enabling researchers to automatically and continuously ingest open government data into an analysis database. The stack follows the modern data engineering standard: Airbyte handles Extract and Load, dbt handles Transform, and Airflow orchestrates the whole pipeline.

03H3 Geospatial Analysis — 城市空間資料的六邊形化H3 Geospatial Analysis — Hexagonalizing Urban Data

使用 Uber H3 六邊形格網系統，把城市開放資料（人行道、人口、交通事故等）轉換成統一的空間格式，讓不同來源的資料可以直接疊合比較。同一套流程分別應用於新竹市與台北西區，產出供研究員使用的時間序列地圖與覆蓋率分析。 Used Uber's H3 hexagonal grid to transform urban open data (sidewalks, population, accidents) into a unified spatial format for cross-layer comparison. The same pipeline was applied to both Hsinchu City and Taipei West District, producing time-series maps and coverage analyses for researchers.

H3 資料處理流程：GeoJSON 原始資料 → 城市範圍篩選 → H3 多邊形填充 → 解析度層級映射 → 覆蓋率 CSV H3 processing pipeline: raw GeoJSON → city boundary filter → H3 polyfill → resolution mapping → coverage CSV

04City AI UI Redesign — Taiwan Island ProjectCity AI UI Redesign — Taiwan Island Project

CityAI 是 CSL 的 AI 輔助城市研究平台：研究員用自然語言詢問問題，後台 Multi-Agent 系統從資料庫抓取 H3 空間資料並渲染到地圖上。我負責這個平台的介面改版，核心問題是：如何讓研究員理解 AI 正在做什麼？ CityAI is CSL's AI-assisted urban research platform: researchers ask questions in natural language, a Multi-Agent system fetches H3 spatial data from the database, and renders it onto a map. I led the UI redesign — the core question being: how do you help researchers understand what the AI is actually doing?

設計問題The Design Problem

原始介面的 Multi-Agent 執行過程完全是黑盒——使用者只看到結果，不知道哪個 Agent 做了什麼、為什麼這樣呈現。同時「單頁版」把聊天框與地圖整合在同一個頁面，需要找到兩者並存的平衡點。 The original interface treated Multi-Agent execution as a black box — users only saw results, with no visibility into which agent did what or why. Meanwhile the "single-page" design had to balance a chat panel and a full map in one view without either feeling cramped.

設計原則：Transparency over Simplicity。研究員需要看到 AI 的推理過程才能信任它的結果——尤其是空間資料的解讀往往高度依賴資料的選擇與處理方式。「讓 AI 過程可見」比「讓介面看起來簡潔」更重要。 Design principle: Transparency over Simplicity. Researchers need to see the AI's reasoning to trust its outputs — especially since spatial data interpretation is highly sensitive to how data was selected and processed. Making the AI process visible mattered more than making the interface look clean.

06反思與收穫Reflections

1. 資料規模不是問題，是設計變數1. Data scale isn't a problem — it's a design variable

第一次處理 350 萬筆資料，才真正理解「開始跑不代表跑得完」。495MB 的 GeoJSON 讓我學會什麼叫做 OOM，也學會了在設計資料流程時就要考慮規模：分批處理、用伺服器而不是本機、選對解析度（res 9 的精度夠嗎？還是需要 res 12？）。 Processing 3.5M rows taught me that "it started running" doesn't mean "it will finish." The 495 MB GeoJSON gave me my first real OOM experience and taught me to design for scale from the start: batch processing, offloading to a server, and asking "is res 9 precise enough, or do we need res 12?" before running anything.

2. 介面是資料的延伸，不是裝飾2. Interface is an extension of data, not decoration

做 UI 設計的時候，我深切體會到：研究員看到的地圖背後，是我在 Pipeline 裡寫的 DAG、是 H3 toolkit 算出的覆蓋率。當你理解資料如何產生，你就會做出更準確的設計決策——比如哪些資料欄位值得在介面上顯示、哪些查詢限制需要在 UI 層面給用戶提示。 While designing the UI, I realized the map researchers see is built on the DAGs I wrote in the pipeline and the coverage ratios the H3 toolkit computed. Understanding how data is produced leads to better design decisions — which fields are worth surfacing in the interface, and which query constraints need to be communicated to the user at the UI layer.

3. 模組化是協作的語言3. Modularity is the language of collaboration

曾經因為程式碼沒有模組化、Git 沒有規範，造成資料庫被誤操作。這件事讓我對「dbt model 化」「封裝 API 為 Python function」「環境隔離」有了不只是技術層面的理解——這些不只是工程實踐，也是讓多人協作不互相踩到的設計。 A database corruption incident from non-modular code and absent Git conventions gave me more than a technical understanding of dbt modeling, API-to-function wrapping, and environment isolation — it showed me that these practices are fundamentally about designing a collaboration that doesn't step on itself.

最意外的收穫：善用 LLM。從問「這個錯誤是什麼意思」到問「幫我設計這個資料流程的架構」，LLM 讓我能在沒有太多前輩指導的情況下自學一整套 data engineering 工具鏈。但前提是你要有足夠的概念基礎來判斷答案是否正確——這就是為什麼理解概念比背指令更重要。 Most unexpected takeaway: using LLMs effectively. Going from "what does this error mean?" to "help me architect this data flow" — LLMs let me self-teach an entire data engineering toolchain with minimal senior guidance. But it required enough conceptual grounding to judge whether an answer was correct, which is exactly why understanding concepts beats memorizing commands.
